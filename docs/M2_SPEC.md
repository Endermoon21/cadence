# Cadence M2: fetch pipeline (CLI)

`cadence fetch` downloads the tracks the ledger says are missing, through the Tidal gate, into staging, then verifies, tags, places and records them. Context: `DESIGN.md` §5 (Fetch, Folder naming, Editions), §6 (gate), §7 (M2).

```
cadence fetch [--artist NAME | --release TIDAL_RELEASE_ID] [--quality HI_RES_LOSSLESS|LOSSLESS|HIGH]
              [--staging DIR] [--library DIR] [--execute] [--limit N] [--include-variants]
```

**Dry run is the default.** Without `--execute` it prints the plan (target path, `would fetch` / `exists, skip`, Tidal track id, duration, destination) and makes no network call, no login and no write. `--library` (else `$CADENCE_LIBRARY`) is needed so it can say whether each target exists; `--staging` (else `$CADENCE_STAGING`) only for `--execute`. There are no built-in paths.

**Plan** (`fetch/plan.py`): one item per recording cluster with no linked file (library-wide), using the canonical recording's Tidal track (latest remaster, `cadence regroup`), preferring album over EP over single over compilation. Variants (instrumental, live, remix...) are left out unless `--include-variants`. Only artists with `tidal_match` auto/manual. Target is `Artist/Album/NN - Title.ext` from `ledger/naming.py`; the title carries Tidal's version (`Song (2009 Remaster)`). Run `cadence sync-catalog`, `link` and `regroup` first, or "missing" is stale.

**Stream** (`fetch/stream.py`): `resolve_stream(session, track_id, quality)` reads `tracks/<id>/playbackinfopostpaywall` with the requested `audioquality` and returns `StreamInfo`. It refuses encrypted streams, previews, non-stereo audio and manifest layouts it does not understand; it never decrypts. Direct-URL manifests are downloaded as is; DASH (hi-res) manifests are fetched as init + numbered segments by plain GET and remuxed (stream copy) by ffmpeg into `.flac`/`.m4a`.

**Run** (`fetch/run.py`): per track: if the target is already on disk or in the ledger, make no Tidal call: `exists` when the ledger links it to this track, `conflict` when it is occupied by anything else (nothing is fetched; if it only becomes occupied after the download, even at the last instant before the link, the verified copy stays in staging and the event and note name its path), `gate.call` the playback request, `gate.call` the download to `staging/<target>.part`, atomic rename in staging, ffmpeg decode check plus duration within 3 s of Tidal's, mutagen tags (FLAC: ALBUMARTIST = primary artist, TITLE, TRACKNUMBER, DISCNUMBER, ALBUM, ISRC; M4A: the equivalent atoms), place into the library. On one filesystem that is `os.link` (no-clobber) then unlink the staged copy. Across filesystems (Unraid: staging on cache, library on the array) it copies to a `.part` file in the library, fsyncs, checks the size, links it into place with no-clobber, and unlinks the source only after the link is committed. Hard links are probed in preflight, and preflight refuses a staging directory that is inside or equal to the library. Then insert the `file` row (`source=tidal`, `match=manual`, `match_score=1`, `quality_requested`, `quality_received`), `fetch.placed` event, commit. It writes only under staging and library and never overwrites or deletes.

**Stops and exit codes.** A 429 (or a paused gate) stops the run with exit 3 and lists the remaining items. A 401 on one track's playback request logs `fetch.blocked` for that track and goes on, unless the 401 body names the token or session: that is an auth failure and stops the run (exit 1). Other per-track errors log `fetch.failed` and go on (exit 1 at the end); a `conflict` also makes the run exit 1, with a line on stderr saying so; three dead connections in a row stop the run. Items whose destination is `fiio` only are skipped until M2b (the holding folder is not built).

**Quality gate.** For LOSSLESS and HI_RES_LOSSLESS requests, a lossy result (AAC) is not placed: it is staged as `<stem> [tidal <id>].m4a` and logs `fetch.held_lossy`, with no `file` row and no library write. A held track is skipped before any Tidal call on later runs. HIGH requests are exempt and place lossy files. Once a FLAC replaces a held copy, the staged AAC is removed (`fetch.stale_held_removed`).

**Naming.** Multi-disc albums use `D{disc}-NN - Title.ext`. The prefix appears only when the release has more than one disc. The disc count comes from Tidal's `numberOfVolumes`, with the highest disc number seen on the release's tracks as a floor (`plan.py`).

## Status (2026-10-27)

- Built: plan, stream resolve, run (gate, staging, verify, tag, place, ledger row, events), lossless-only gate, held files, cross-device placement, disc-aware names, legacy matching for multi-disc albums (exact title and track number) plus the duration rule. A linked (already owned) file is a near-duplicate only of an unowned track whose title is related but different; with an identical normalized title it is never a claimer and does not count toward ambiguity. A file that matches more than one recording cluster of the artist (by name, tag, or duration; owned or missing; in any release group its folder name matches) claims none of them. A file claims a cluster if it fits any non-variant row of it (available or not); the representative row only decides the target path and tags. Claims and ambiguity are computed over the artist's own releases only, never widened by `--release` (even an appears-on release), so `--scope` and `--release` choose which items are planned and never which tracks are owned. A title that normalizes to nothing (`?`) matches only a file whose raw title is the same (`?`), never an empty or different one (`...`). A cluster that exists only on an appears-on release (so has no own group) is claimed by a file in that release's own folder, unless an own cluster claims the same file; when a cluster is on an own release too, the planned row is the own release's, so `--release <appears-on>` never moves the target. Pick order for the planned row: the cluster's non-variant rows first (all its rows only if it has none), own-release rows among them, then all of them as the fallback; so a variant on an own release never hides the non-variant row of an appears-on release named by `--release`, and `--include-variants` picks the same non-variant row for a mixed cluster (variant-only clusters are planned by it as before). A default run does not load appears-on rows, so a cluster whose only own row is a variant is not planned there.
